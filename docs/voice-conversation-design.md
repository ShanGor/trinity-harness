# 电话中的回答与交互设计

> 2026-11-02 · 第一阶段已实现，真实模型与设备验收待完成；第二阶段仍为条件性提案。本文覆盖电话的内容生成和交互，不改变当前电话状态机。媒体能力以 [voice-call-design.md](voice-call-design.md) 和 [webrtc-media-design.md](webrtc-media-design.md) 为准。

## 1. 决策：先给能听懂的结论，每次只展开一个层次

电话不是把专业报告逐字念出来。推荐默认「简短对话」：先直接回答，再给最关键的理由或下一步；复杂内容留在当前聊天的文字详情、文件和证据入口。用户随时可以要求「详细讲」「举个例子」「继续」「先说结论」，不用每次进入设置。

专业程度不降低：保留会影响判断的条件、风险、不确定性和必要数字；减少一口气听不住的术语、目录和旁支信息。不能把没有核实的结论说得更确定，也不能只为听起来顺口而省略审批或关键限制。

建议默认值是待真人评测的目标，并非现有性能承诺：

| 情境                       | 首次口头输出                                                    | 接下来                                       |
| -------------------------- | --------------------------------------------------------------- | -------------------------------------------- |
| 简单问答                   | 1–2 个短句，通常 5–10 秒                                        | 回到收听，不固定追加「还需要什么」           |
| 专业解释/建议              | 一小段，通常共 40–80 个中文字、10–20 秒，含必要的一个澄清问题   | 给一条有用建议或关键理由，确有分支才问一次   |
| 操作指导/排错              | 先说当前一步及成功标志；通常 10–20 秒                           | 等用户提供观察结果，再决定下一步             |
| 代码、报告、研究等执行任务 | 简短确认；必要时给真实进度；完成后用 10–25 秒说明结果及重要限制 | 完整产物和验证在文字中，已授权工作持续到完成 |
| 用户明确要求完整讲解/朗读  | 按用户要求，围绕一个子问题讲 30–60 秒左右                       | 在语义边界停下；用户说「继续」，无需重复起点 |

时长、字数是生成指引，不能靠硬截取 TTS 文本达成。句子可稍超目标以完整表达关键条件；混合语言、数字和术语按实际听感评估，不机械换算。需要紧急完整表达的安全信息允许超限。

## 2. 一次专业问题的体验

用户：「RAG 和微调有什么区别，我们该选哪个？」

助手：「查内部资料一般先考虑 RAG，微调更适合调整回答方式。你们主要想解决知识过期，还是回答方式不符合要求？」

到这里结束这次回答，释放播放并恢复收听。用户说「知识经常更新」，才继续讲更新和权限相关的一层。不要在用户尚未选择时自动念完整技术选型报告，也不要把「通常适合」讲成无条件保证。

用户：「我想学好英语，应该从哪里开始？」

助手：「先从每天听一小段简单英语、跟读几句开始，容易坚持。你学英语主要为了工作、考试，还是日常交流？」

不要在得到用户目的之前，同时展开听力、口语、词汇、语法、教材和工具清单。简短模式不是将一份完整报告的各节压成短句；它只回答当前最有用的一点。用户明确要求完整方案时按要求展开，必要条件和风险仍可超出目标。

用户：「把鉴权问题修掉，再给我说明。」

助手可以说「我先检查鉴权流程，修好后告诉你结果」，然后完成已授权的检查、修复和验证，不为每一步制造电话问答。结果口头先说修复了什么、验证是否通过、是否还有风险；文件差异和完整日志在当前 Chat/Work 查看。遇到真实权限审批才进入现有可视审批流程。

## 3. 控制与状态

通话面板保留收听、思考、播放、审批和错误状态，提供两个内容控制：

- 「简短 / 详细」：本次电话的解释深度，默认简短；当前用户明确要求优先。它与声音风格分别设置，不能把女声/语速当成答案长度。
- 「查看详情」：展开同一回答中的文字详情和 Sources/View evidence。未提交的新输入仍留在草稿里。

正常回答或澄清问题播放完毕，并且当前 Agent turn 已结束后，未静音、未挂断且无待决审批的电话自动恢复麦克风监听。用户可直接回答澄清问题或提出新问题，无需点击「继续听」或再次开始录音；不增加这个按钮。用户说「继续」表示请求展开解释，与自动恢复监听是两个独立动作。静默监听不产生新请求，也不自动让 Trinity 继续讲话；批量兜底录音到达 60 秒上限时，未检测到说话的片段在本地丢弃并继续监听，不送 ASR。

播放时保留现有「打断」；当前没有 AEC/barge-in，界面必须说明需要点按。未来可设计「先听我说」：在可确认输出已经稳定结束的边界停播，并按现有取消机制处理仍在运行的 Agent；取消必须等 terminal 确认，不能靠停音宣称任务停了。不要把现有取消按钮静默改成仅停止扬声器。挂断仍只释放媒体，已接受的任务继续执行。

用户未开口时保持安静收听。可选的轻量视觉提示不生成新 prompt、不触发额外 LLM 调用、不无限重问。拒绝麦克风、断线、字幕未确认、静音、挂断和会话切换继续清理未提交的识别集合。保持当前 1.8 秒静音端点与 confirmed ASR 规则，不在本提案中同时调整。

## 4. 生成方式：在生成时决定说什么

不采用「先写长文，然后截断前几句」：它可能读完开场和铺垫，却没说结论。也不默认增加一个摘要模型去重写专业答案：这会增加首音等待、费用和正文/语音不一致的机会。

建议分两阶段实现，均复用普通 Agent Loop、同一 prompt 和单条最终 Assistant 回答：

### 第一阶段：简短回答策略

由已鉴权的前端随本次普通 ACP prompt 提交有界的 delivery hint（例如电话、简短/详细），服务端验证并与该次已提交请求一起落事件，再用于可重放的模型上下文。不能仅把「现在是电话」藏在服务器内存或浏览器状态，也不能篡改 ASR 原文来伪装用户指令。旧客户端缺省沿用现有行为；挂断后的后续文字请求不继承电话 hint。团队与个人会话都按当前用户请求生成，无需导入个人记忆。

模型按「结论 → 一项理由/下一步 → 必要时一个问题」组织最终正文；完成真正的任务后才结束 turn。进度本身也要短，但不能编造进度或反复念等待提示。复用现有已稳定句子的流式合成；完整可读句形成即入队，不等整段报告完成。详细产物仅在任务确实需要时生成文件，并在同一最终回答给出链接，避免为了每个电话问题额外造文件。

### 第二阶段：同一回答的口头段与文字详情

当第一阶段的真人评测证明需要「简短口述 + 完整屏幕答案」时，扩展 contracts 的类型化内容块与 append-only 事件：例如 `spoken`、`detail`，并给出稳定块 ID、单调序号、完成边界与引用关联。名称只是提案，实施前要评审具体 Zod/事件版本及迁移兼容方案。

同一次模型生成先提交简短的口头段，再提交必要的文字详情；文字客户端把它们渲染成同一条 Assistant 回答，电话只合成标为口头的稳定内容。不得用任意 Markdown 标记、代码围栏或不入日志的前端摘要来识别口头段。屏幕必须能查看实际说出的原文，口头结论的来源和细节引用仍可追溯。

只有完成且不可修订的块才能播放。追加式流中已说的内容不能静默覆盖；后续发现更正须明确说出修正。引用链接、代码、表格和日志留在 detail；决定行动或影响结论的限制必须进入 spoken。工具输出与审批不自动转成朗读文本。

### 未讲完与未做完分别处理

用户口头说「继续」时，通过普通用户 prompt 展开已授权上下文中的解释，不重复工具副作用；保存完整原始请求、更正和任务状态。没有收到用户新请求时不自动创建 continuation turn。用户先前要求的长任务仍按原请求执行完毕，不能借口「电话要短」提前结束或改成反复追问。

若口头段已经播完，但文字详情/任务尚未结束，面板显示「仍在整理详情」；当前会话仍遵循真实 busy/队列语义，不假装已可并发执行新 turn。用户的新问题走现有持久队列，或显式打断后等待终态；不启用第二个隐藏 Agent、不靠前端恢复收听绕过当前半双工状态机。更好的计算/收听并行能力需要单独评审。

## 5. 播放节奏与声音

每个完整句子复用同一电话开始时确定的声音设置；设置修改在下次电话生效，避免句间换声。部署默认说话人是用户提供的 Peach 录音，经 Qwen3-TTS Base speaker-embedding prompt 克隆；默认交付目标是标准普通话、专业沉稳、亲切耐心和稳定适中的讲解速度。中文指引目标为每分钟约 220–260 字，句内、句间不突然加速、放慢或拖长字音。账户声音偏好只控制合成风格，不改变回答语言、任务授权或 Agent 行为，也不替换部署默认说话人。

完整句子中的顿号和中英文分号不作为单独合成边界，避免将列举项切为多个短请求；完整句号、问号、感叹号、换行和既有有界长段切分继续生效。本地 TTS 服务加载 Qwen3-TTS Base 和预计算的 Peach speaker-embedding prompt，按声音描述固定采样起点，并在 GPU 锁内保存、恢复 RNG 状态；HTTP text/language/instruct 契约不变。speaker embedding 提供参考音色条件；x-vector-only 下的语速/表达指令遵循仍须真人听测，不代表精确语速保证。

语义段之间允许自然停顿，不插入人为长等待。语音队列必须有界并沿用 call/session/response epoch 取消；超过预计 25–30 秒的播放积压时优先控制后续生成的解释长度或停止预合成，不丢弃中间的关键内容，不切断当前句子伪装自然结束。详细模式可调整目标，但仍要在话题边界提供停下的机会。队列上限及背压机制需结合真实 TTS 延迟在实施时确定。

当前默认服务使用 Peach 的 Base speaker-embedding prompt；生成时可直接复用，不需重新提取参考特征。VoiceDesign 仍可通过显式模型配置用于独立试听。参考音频和 prompt 是本地 TTS 部署资产，需限制主机访问并按用户要求删除；更高质量的 instruction/韵律控制可在取得准确参考转写后评估 ICL 模式。

## 6. 第一阶段实现与后续边界

- contracts `prompt-delivery.ts` 定义严格有界的 `{mode: 'phone', depth: 'brief' | 'detailed'}`；shared 转出，client-acp 随普通 prompt 提交。服务端在会话鉴权与输入校验后，将可选 `delivery` 同请求一起写入 `message/user` 或 Main 的 `prompt/queued`。Main 提升、worker 重启和同一请求续跑保留字段；旧事件/客户端不带字段时保持原行为。不新增数据库列或迁移；先部署理解该字段的 server/worker 读端，再部署 Web 写端。
- Loop 每次模型调用从当前 `promptSeq` 对应的已提交用户事件派生电话生成指引，覆盖工具执行前后。ASR 原文与用户目标保留；用户明确要求优先，长度为生成目标，不截断正文/TTS、不增加摘要模型、不更改审批或提前结束任务。挂断后新的文字请求不带 hint。
- 电话默认简短，深度选择只影响本次电话的下一次提交；重拨恢复简短。声音风格仍为单独的账户设置。查看详情最小化面板，显示同一条 Assistant 正文及现有 Sources/View evidence；文字草稿、焦点和暂存附件保留，电话提交不携带这些附件。
- 回答或澄清问题播放完且 turn 结束后自动恢复监听，无需按钮；用户可直接回答或说「继续」走普通请求与已授权上下文。第二阶段仅保留有来源关联的类型化口头/详情块提案，不增加「继续听」按钮；未启用自动续讲或隐藏 Agent。
- 播放仅保留一个正在合成/播放的有界句子；原文中未播放的稳定文本延迟分句，上一句播放完成后才发起下一次合成，不预合成后续音频。待播文本不是音频队列；保留中间内容与工具归档顺序，沿用 epoch 取消、挂断和重连 fencing。实际发言时长仍需真实模型与设备验收。

## 7. 验证与落地顺序

先实施并验证统一默认风格和账户偏好（独立于本文的内容生成提案）。随后才能按本提案实现电话 hint、简短生成指引及控制；最后根据评测决定是否增加类型化口头/详情块。本次已实现第一阶段电话 hint、简短生成指引及「简短 / 详细」「查看详情」控制。

确定性验收覆盖：hint 来源与重放、旧客户端兼容、挂断后的普通请求、原始用户目标保留、单条 Assistant 投影、继续解释不重复操作、审批不能口头自动通过、稳定块播放、更正与断线、队列背压、epoch 失效、草稿/焦点及多会话隔离。真实模型评测覆盖闲聊、专业解释、排错、多步骤操作、研究报告、必要风险与长篇朗读。

真人电话测试至少覆盖桌面、Android Chrome、iOS Safari，比较现有长文朗读与简短生成：首个有意义音频延迟（从 confirmed 用户轮次结束计时）、一次连续发言时长、打断率、重复澄清率、任务完成率、关键条件遗漏与用户理解。可先以默认专业答复 P90 ≤25 秒、用户能复述主要结论为试验目标；延迟与比例门槛须经真实设备基线校准，不能把 fake TTS/单次演示当作通过。采集有同意的有限评测材料，不把音频、原始内容或用户身份写入常规指标。
