# Guest desktop interaction

Status: **enabled on the local development node; not a production isolation guarantee**. The authenticated viewer, guest browser route, desktop process manager and blocked-command handoff are connected. The matching image passed direct-VMM and jailer tests in two disposable generations, and the assigned owner's live Browser Runtime route returned a desktop frame after a fresh VM generation. Production isolation and the remaining acceptance gates below still apply.

## Goal and evidence

The controlling human needs to see and operate the guest's actual desktop, including browser chrome, native menus and JavaScript alert/confirm/prompt dialogs. A desktop must not replace the model's typed browser/evidence path or make user-only pixels available as model evidence.

A disposable local experiment on 2026-10-27 launched the pinned Zendriver and Chrome with `headless: false` on an Xvfb display, exposed that isolated display through x11vnc, and triggered a JavaScript `prompt()` through the existing browser input path. The opt-in `apps/guest-runtime/test/desktop-dialog.integration.test.ts` captures the X11 framebuffer and uses the bounded `DesktopRfb` input adapter with operator-selected test binaries and a temporary private Unix RFB socket. It types Unicode into a prompt, dismisses an alert, and accepts and cancels confirm and prompt dialogs while the corresponding browser calls are blocked. Input completion confirms protocol delivery only; a failure after dispatch has an unknown effect. The disposable direct-VMM Firecracker check also exercised a supervisor handoff during a real blocked Chrome prompt with isolated PostgreSQL records and advisory locks, the authenticated Node Agent request handler with synthetic assignment metadata, native bookmark navigation, workspace and Chrome access restrictions, and bookmark persistence across two generations. It does not establish a production image, actual deployment identity routing, jailer isolation or production readiness.

## Boundaries

- Run a graphical display and a window manager inside the assigned personal Firecracker guest. Start managed Chrome headed on that display using the same tenant/user profile and pinned Zendriver; retain the exclusive profile lease, isolated guest environment, configured egress and existing model browser driver. Do not attach to the host desktop or a user's host Chrome. The opt-in image runs the browser supervisor as UID 1001 and Chrome as UID 1002. A narrowly scoped guest firewall permits only UID 1001 to connect to Chrome's fixed loopback debugging port; the Chrome wrapper drops all capabilities before launching UID 1002. The workspace remains UID 1000. These controls and the host-CID vsock guard require real guest validation before release.
- The viewer receives only the authenticated owner's desktop. Guest screen pixels and input text are ephemeral user data, never ACP/model evidence, event payloads, diagnostic logs or shared across tenants. Authorize the session, owner, environment assignment and generation at connection establishment and continuously for a live stream; close on revocation, disconnect, lease expiration, generation change or runtime shutdown.
- A raw VNC WebSocket is not an adequate control boundary. A noVNC client can send keyboard, pointer and clipboard messages directly; hiding its controls or setting a client-side view-only flag does not enforce authorization. Desktop input passes server-side control checks, per-input sequence/reservation and outcome handling. The viewer polls bounded PNG frames over its existing authenticated request path; it never receives RFB bytes or an endpoint. Pictures are read directly from the private X11 display because the x11vnc framebuffer was observed to remain stale after a dialog closed. Large pictures progressively reduce colour precision to fit the existing frame limit without changing dimensions or pointer coordinates. There is no general clipboard, desktop resize or file transfer API. To enter composed Unicode reliably, a fenced text action briefly owns the guest's private X11 clipboard and sends a paste to the focused window; this replaces any prior guest clipboard contents, never reads the host clipboard, and removes the temporary data when the selection is consumed or the request ends. Keyboard input is checked against the focused X11 window captured with the frame; this does not independently identify the focused DOM element within that window.
- The private RFB input adapter ignores bounded asynchronous bell messages while waiting for a framebuffer acknowledgement, and x11vnc is configured not to emit bells. An X11 bell was reproduced causing a valid subsequent input to be quarantined when the adapter treated the bell as an invalid acknowledgement. This handling does not retry uncertain input or weaken the existing quarantine rules.
- Browser control remains anchored to the authenticated owner's Main session. Existing PG epoch, exclusive human ownership, lease, per-origin authorization, observation invalidation and unknown-effect rules remain authoritative. Pixels alone do not authorize input: map against a recent desktop frame and generation/geometry, reject stale controls, and cancel active pointer gestures on loss of control or size change.
- Convert scaled viewer coordinates to the nearest whole source pixel and clamp to the last pixel before sending clicks, drags or anchored wheel input. CSS layout and local Fit/zoom commonly produce fractional coordinates; the guest RFB adapter requires integers. Sending those fractions previously failed before dispatch and quarantined control, including clicks on Chrome's Restore button. The bell fix above did not resolve this separate viewer defect.
- Fail closed on malformed, oversized or unsupported protocol messages, missing state, uncertain revocation or transport errors. A reconnect can read state and obtain a fresh view; it cannot replay pointer, keyboard or takeover effects. An input whose outcome is uncertain quarantines control and is not automatically retried.
- Keep the VNC/display service private to the guest and its authenticated relay. Do not expose a guest-controlled target address, a host TCP listener, the MCP/CDP endpoint, or unauthenticated RFB to the web. Isolate display access from workspace processes; running Chrome, the VNC server and untrusted workspace code under the same unrestricted Unix identity is not sufficient to enforce exclusive input authority.

## The blocked-dialog handoff

A native dialog can block a Zendriver command while the current browser supervisor holds the shared operation lock. The opt-in implementation fences the in-flight agent operation without cancelling its current driver call and uses a second distributed lock for human intervention. The original command remains reserved until it settles and the user returns or pauses control; its result is reported as an unknown effect and is not replayed. Returning control requires the in-flight command to settle, followed by fresh per-chat observations. Failed or disconnected desktop input is quarantined. If the driver or its lock is lost, the session is disposed and input fails closed. The optional `TRINITY_GUEST_PG_TEST=1` real-guest check uses isolated PostgreSQL tables, advisory locks and the bearer-authenticated Node Agent request handler with synthetic metadata; deployed identity routing still needs end-to-end acceptance.

## Delivery and acceptance

The owner can watch an existing desktop before taking control and after returning control to the agent. The optional `ManagedBrowserSession.readOnlyFrame` capture uses the private guest desktop RPC independently of blocked agent commands, serialized with desktop intervention. The supervisor checks authenticated ownership and the active runtime binding before and after capture and discards pixels if generation or control changes. Read-only frames never become persisted input targets, keyboard tokens, model evidence or event payloads. Watching neither starts a browser nor changes control; another view cannot watch a human-controlled desktop. Local zoom/pan remains available, while remote pointer, wheel, keyboard and browser controls require explicit takeover and a fresh input frame. Deploy matching contracts/core, Web and Browser Runtime and restart the resident runtime; no guest image or migration is required.

The 2026-10-27 Restore follow-up reproduced the actual Chrome crash-recovery popup in a disposable profile. Fractional scaled input failed at the guest adapter; a click using the corrected viewer mapping dismissed Restore, and a subsequent desktop click succeeded. Deterministic tests cover fractional layout/zoom, edge clamping and a scaled desktop click retaining control; desktop UI fakes now reject fractional coordinates like the real guest. This correction is served by the running development Web app and requires a fresh frontend module; it does not require replacing the guest image. The reproduction used a temporary profile, rather than replaying the owner's earlier unknown inputs.

Build and pin the display, window manager, Chrome and VNC components in the guest image; select them from authenticated deployment metadata, not model arguments. The experimental `--desktop` image records its package versions and executable hashes. `GUEST_DESKTOP_ENABLED=1` selects its separate browser route; the default remains the existing headless path, and a configured desktop failure never falls back to it. Roll out matching readers before writers and use the existing drain, confirmed-stop, immutable-image and fresh-generation procedure, preserving the user's data disk. The browser profile migration changes file ownership inside that disk; downgrade requires an explicitly reviewed ownership restoration before an older guest can use it. On 2026-10-27 the local development node was drained, its previous image and an offline copy of the user's disk were preserved, the new image passed jailer acceptance, and matching Node Agent and Browser Runtime processes were restarted. The user's existing disk was retained and booted in a fresh generation.

The live Chrome connection and the in-flight intervention gate are owned by one Browser Runtime process. Until authenticated owner-aware routing exists, all calls for an active browser must reach that same process; a load balancer distributing these calls across independent runtimes cannot provide the handoff. Run a single Browser Runtime for this opt-in path and retain the PostgreSQL locks as fencing rather than treating them as a routing mechanism.

Acceptance must include real guest tests for alert, confirm and prompt accept/cancel, a prompt opened during an agent action, bookmark menu and new-tab switching, input while Chrome's CDP call is blocked, desktop resize and coordinate accuracy, Unicode input, disconnection during an input, stale/duplicate requests, takeover/release/lease expiration, revoked ownership and stale VM generations. Verify that a second view or originating chat cannot control or receive private pixels; verify that raw RFB input, clipboard and resize cannot bypass fencing. Test disposal, process exit and profile persistence across a fresh guest generation. Separately validate jailer/network isolation and production storage; a local Xvfb fixture does not prove them.
